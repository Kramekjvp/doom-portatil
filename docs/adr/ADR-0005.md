# ADR-0005: Suporte a múltiplos jogos (extensão pós-MVP)

## Status
Proposta — extensão pós-MVP, não iniciada. Só entra em desenvolvimento
depois que as Fases 0–7 originais estiverem fechadas com folga (ver risco
"escopo inflar demais" no roteiro original).

## Contexto
Vontade de tornar o console mais genérico, somando ao Doom pelo menos mais
dois jogos: um título antigo de Game Boy (ex.: Pokémon, a partir de ROM
extraída de cartucho próprio) e Tetris.

## Alternativas consideradas

**RetroArch + core libretro (gambatte)**
Solução completa, com save states e suporte a vários consoles. Em troca:
interface própria pesada, mais dependências, e foge do estilo enxuto
("sem desktop", poucas dependências) do resto do projeto — provavelmente
desperdiça boa parte da RAM da Pi Zero 2 W (512MB) só com o frontend.

**Peanut-GB (biblioteca single-header em C99)**
Emulador de Game Boy original (DMG) — mesma geração do Pokémon
Vermelho/Azul/Amarelo. Leve, rápido (já usado até em microcontroladores),
sem interface própria: o projeto escreve a "cola" de vídeo/áudio/input,
no mesmo espírito do `doomgeneric`.

**Tetris: ROM de Game Boy vs. clone open-source**
Rodar o cartucho original de Tetris no mesmo Peanut-GB reaproveita 100% do
trabalho do item anterior, mas mantém a dependência de uma ROM comercial.
Um clone de código aberto rodando direto no framebuffer evita essa questão
por completo, ao custo de implementar (ou adaptar) a lógica do jogo.

## Decisão
- **Emulador de Game Boy:** Peanut-GB, pelos mesmos motivos que levaram ao
  `doomgeneric` — leve, portátil, poucas dependências.
- **Tetris:** clone de código aberto rodando direto no framebuffer,
  evitando depender de ROM comercial para esse jogo.
- **Pokémon:** via Peanut-GB, com ROM extraída de um cartucho de
  propriedade do usuário (dump legal) — nunca de fonte de terceiros na
  internet. A origem da ROM é responsabilidade de quem for rodar o
  console, fora do escopo técnico deste ADR.
- **Seleção de jogo:** um launcher simples e próprio (não um frontend
  completo tipo EmulationStation), que lista as opções e dá `exec()` no
  jogo escolhido — navegado pelos mesmos botões físicos.

## Consequências
- Reaproveita 100% do protocolo serial (ADR-0003), do daemon uinput e do
  firmware do ESP32 — o teclado virtual não sabe (nem precisa saber) qual
  programa está rodando do outro lado, então nenhuma dessas camadas muda.
- Cada jogo implementa seu próprio backend de vídeo seguindo o mesmo
  padrão de "desenhar num framebuffer" já usado no `pi-doom/` (ADR-0002).
- Adiciona um componente novo ao repositório: o launcher.
- Estrutura de pastas proposta quando esta extensão for implementada
  (ainda não criada — só planejamento):
  ```
  pi-doom/
  ├── launcher/           # menu que lista e inicia o jogo escolhido
  ├── games/
  │   ├── doom/           # o que hoje é pi-doom/doomgeneric/
  │   ├── gameboy/        # Peanut-GB + backend de framebuffer
  │   └── tetris/         # clone open-source
  ├── protocol.py         # sem mudanças
  ├── serial_daemon.py    # sem mudanças
  └── tests/
  ```
- Escopo real, não trivial — tratar como fase separada e opcional, não
  misturar com o cronograma das Fases 0–7.
